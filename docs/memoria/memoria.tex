\subsection{Comprobaciones e inicialización}
Para la carga de la imagen, previo a su procesamiento, se empleó la carga de \texttt{CImg} controlando las posibles excepciones de lectura que puede producir dicho método:

CImg<data_t> srcImage;
try {

} catch (CImgException& e) {

\vspace{2ex}

\noindent En caso de que \texttt{CImg} lance una excepción, se \textit{cacheará}, avisará al usuario y finalizará el programa de forma controlada. En caso contrario, entonces se crea un objeto \texttt{CImg} con el que se trabajará posteriormente.\vspace{2ex}

\noindent Asimismo, se modificó el tipo de dato empleado de \texttt{float} a \texttt{double}. Se definieron también los pesos para las componentes de color y el brillo máximo, como se muestra a continuación:

\begin{lstlisting}[style=cppStyle]
#define R_WEIGHT 0.3

#define B_WEIGHT 0.11
#define MAX_BRIGHTNESS 255.0
\end{lstlisting}
\vspace{2ex}

Para medir el tiempo de ejecución, se emplearon las funciones \texttt{clock\_gettime()} con los parámetros \texttt{CLOCK\_REALTIME} y las direcciones de memoria de las variables. En caso de error, se muestra un mensaje y se finaliza la ejecución. 
Se calcula el tiempo transcurrido y se muestra por la salida estándar:

elapsedTime = (tEnd.tv_sec - tStart.tv_sec) +

\subsection{Implementación del algoritmo}
El algoritmo implementado corresponde al filtro de inversión en escala de grises. Para cada píxel de la imagen, la función \texttt{filter} calcula una luminosidad ponderada a partir de las componentes RGB. Para ello, se emplean los coeficientes definidos previamente. El valor resultante se invierte respecto al brillo máximo y se asigna a las tres componentes del píxel en la imagen de salida.

\begin{lstlisting}[style=cppStyle]
void filter (filter_args_t args) {
    for (uint i = 0; i < args.pixelCount; i++) {
        data_t L = *(args.pRsrc + i) * R_WEIGHT + 
                   *(args.pGsrc + i) * G_WEIGHT + 
                   *(args.pBsrc + i) * B_WEIGHT;
        
        L = MAX_BRIGHTNESS - L;

        *(args.pRdst + i) = L;
        *(args.pGdst + i) = L;
        *(args.pBdst + i) = L;
    }
}
\end{lstlisting}
\vspace{2ex}

\noindent Dado que el tiempo de ejecución debía situarse entre 8 y 15 segundos, se realizó un bucle de 250 iteraciones de la función \texttt{filter} para mantener el tiempo dentro del rango esperado:
\begin{lstlisting}[style=cppStyle]
for (int i = 0; i < N_ITERATIONS; i++) {
    filter(filter_args);
}
\end{lstlisting}
\vspace{2ex}

\subsubsection{Optimización SIMD}
Para la optimización SIMD, se ha empleado la librería \texttt{immintrin.h} que proporciona acceso a las instrucciones \texttt{SSE} y \texttt{AVX}. Se han empleado paquetes de 128 bits (\texttt{\_\_m128d}) para procesar dos valores \texttt{double} simultáneamente. El objetivo es aprovechar el paralelismo de datos a nivel de instrucción para reducir el número de iteraciones necesarias procesando múltiples píxeles en cada ciclo.\vspace{2ex}

\noindent Para la inicialización de los vectores, las constantes de algoritmo se cargaron replicando el valor en ambos elementos del vector:
\begin{lstlisting}[style=cppStyle]
typedef __m128d simd_t;

const simd_t r_weight = _mm_set1_pd(R_WEIGHT);
const simd_t g_weight = _mm_set1_pd(G_WEIGHT);
const simd_t b_weight = _mm_set1_pd(B_WEIGHT);
const simd_t max_brightness = _mm_set1_pd(MAX_BRIGHTNESS);
\end{lstlisting}
\vspace{2ex}

\noindent Para tener un acceso eficiente a los datos, se utiliza \texttt{\_mm\_malloc()} con alineamiento a 16 bytes (tamaño de \texttt{\_\_m128d}). También se asegura el tamaño del buffer de destino para que tenga capacidad suficiente:
\begin{lstlisting}[style=cppStyle]
uint pixelCountAligned = ((filter_args.pixelCount + ITEMS_PER_PACKET - 1) / ITEMS_PER_PACKET) * ITEMS_PER_PACKET;
pDstImage = (data_t *) _mm_malloc (pixelCountAligned * nComp * sizeof(data_t), 16);
\end{lstlisting}

\noindent El bucle principal del filtro procesa la imagen en paquetes de dos píxeles. Para cada paquete, se cargan los valores RGB mediante \texttt{\_mm\_loadu\_pd()}, se calcula la luminosidad ponderada con \texttt{\_mm\_mul\_pd()} y \texttt{\_mm\_fmadd\_pd()} y finalmente se invierte con \texttt{\_mm\_sub\_pd()}. Los resultados se almacenan directamente en las tres componentes de salida:
\begin{lstlisting}[style=cppStyle]
const uint nPackets = (args.pixelCount / ITEMS_PER_PACKET);
simd_t vr, vg, vb, L;

for(uint i = 0; i < nPackets; i++){
    const uint pos = i * ITEMS_PER_PACKET;
    
    vr = _mm_loadu_pd(args.pRsrc + pos);
    vg = _mm_loadu_pd(args.pGsrc + pos);
    vb = _mm_loadu_pd(args.pBsrc + pos);
    
    L = _mm_mul_pd(vr, r_weight);
    L = _mm_fmadd_pd(vg, g_weight, L);
    L = _mm_fmadd_pd(vb, b_weight, L);
    L = _mm_sub_pd(max_brightness, L);
    
    *(simd_t*)(args.pRdst + pos) = L;
    *(simd_t*)(args.pGdst + pos) = L;
    *(simd_t*)(args.pBdst + pos) = L;
}
\end{lstlisting}

\noindent Dado que el número total de píxeles puede no ser múltiplo exacto de 2, hay un bucle residual que procesa los píxeles restantes de forma escalar, empleando la misma lógica que en la versión monohilo. Finalmente, se libera la memoria alineada con \texttt{\_mm\_free()} para evitar fugas de memoria. A continuación, se muestran las imágenes resultantes:

\subsubsection{Paralelización Multihilo}
Para la paralelización multihilo, se utilizó la librería \texttt{pthread.h} para crear y gestionar múltiples hilos de ejecución. El objetivo es dividir la carga de trabajo entre varios núcleos del procesador, empleando 8 hilos de ejecución (\texttt{NUM\_THREADS = 8}) para distribuir la imagen en fragmentos que se pueden procesar de forma concurrente.\vspace{2ex}

\noindent La estructura \texttt{filter\_args\_t} se amplió con dos campos adicionales (\texttt{start} y \texttt{end}) que delimitan el rango de píxeles que cada hilo debe procesar, para trabajar sobre porciones independientes de la imagen:
\begin{lstlisting}[style=cppStyle]
typedef struct {
	data_t *pRsrc;
	data_t *pGsrc;
	data_t *pBsrc;
	data_t *pRdst;
	data_t *pGdst;
	data_t *pBdst;
	uint pixelCount;
	uint start, end;
} filter_args_t;
\end{lstlisting}
\vspace{2ex}

\noindent La función \texttt{thread\_filter()} se ejecuta en cada hilo, donde recibe los punteros a los datos y rango de píxeles a procesar. Primero ajusta los punteros aplicando el \textit{offset start}, calcula la longitud del segmento y procesa los píxeles dentro de ese rango aplicando el mismo algoritmo que en la versión monohilo:
\begin{lstlisting}[style=cppStyle]
void* thread_filter(void* args){
    filter_args_t* tArgs = (filter_args_t*) args;
    
    data_t *pR = tArgs->pRsrc + tArgs->start;
    data_t *pG = tArgs->pGsrc + tArgs->start;
    data_t *pB = tArgs->pBsrc + tArgs->start;
    data_t *pRdst = tArgs->pRdst + tArgs->start;
    data_t *pGdst = tArgs->pGdst + tArgs->start;
    data_t *pBdst = tArgs->pBdst + tArgs->start;
    
    uint length = tArgs->end - tArgs->start;
    
    // Procesamiento análogo al filtro monohilo
    
    pthread_exit(NULL);
}
\end{lstlisting}
\vspace{2ex}

\noindent La función \texttt{execute\_multithreaded\_filter()} se encarga de coordinar la ejecución paralela. Para ello, calcula los píxeles por hilo, crea los hilos con \texttt{pthread\_create()} y espera a que terminen con \texttt{pthread\_join()}. El último hilo se encarga de procesar cualquier píxel restante en caso de que el total no sea divisible por el número de hilos:
\begin{lstlisting}[style=cppStyle]
void execute_multithreaded_filter(filter_args_t* filter_args, uint pixelsPerThread) {
	pthread_t threads[NUM_THREADS];
	filter_args_t thread_args[NUM_THREADS];
	
	for (uint t = 0; t < NUM_THREADS; t++) {
		thread_args[t] = *filter_args;
		
		thread_args[t].start = t * pixelsPerThread;
		thread_args[t].end = (t == NUM_THREADS - 1) ? filter_args->pixelCount : (t + 1) * pixelsPerThread;
		
		if(pthread_create(&threads[t], NULL, thread_filter, &thread_args[t]) != 0){
			fprintf(stderr, "Error creating thread");
			exit(EXIT_FAILURE);
		}
	}
	
	for (uint t = 0; t < NUM_THREADS; t++) {
		if (pthread_join(threads[t], NULL) != 0) {
			fprintf(stderr, "Error joining thread %d\n", t);
			exit(EXIT_FAILURE);
		}
	}
}
\end{lstlisting}
\vspace{2ex}

\noindent Finalmente, en la función principal, se calcula el número de píxeles por hilo y se llama a \texttt{execute\_multithreaded\_filter()} para iniciar el procesamiento paralelo. Esta función se ejecutará el número de veces fijado para medir el tiempo total de ejecución. A continuación, se muestran las imágenes resultantes:

\noindent A partir de los datos obtenidos, se calcularon una serie de medidas estadísticas para resumir la información, aplicando medidas de centralización y dispersión. La implementación multihilo ha mostrado una mejora de rendimiento 
de aproximadamente 1.58 respecto a la versión monohilo. Aunque esta 
mejora es significativa, está muy lejos del teórico ideal de x16 aunque 
se hayan utilizado 8 hilos por motivos que se tratarán más adelante. Esto resulta en una eficiencia del 19.75\%, lo cual indica que existen cuellos de botella en algunos puntos del proceso. Las posibles causas incluyen:
\begin{itemize}
    \item \textbf{Contención de recursos}: Aunque cada hilo trabaja sobre un segmento independiente de la imagen, 
    a partir de cierto número de hilos aparece contención 
    en la memoria caché. Cuando demasiados hilos acceden simultáneamente 
    a regiones de memoria cercanas aumenta el número de fallos de caché. Como 
    el rendimiento pasa a estar limitado por el subsistema de memoria, hemos decidido 
    limitar el número de hilos a 8.
    \item \textbf{Overhead de creación/destrucción de hilos}: En cada iteración se crean y destruyen 8 hilos, lo que introduce un coste adicional en el tiempo total. Se ha mantenido este enfoque por indicaciones presentes en la rúbrica de evaluación.
    \item \textbf{Tamaño de trabajo insuficiente por hilo}: Dado que la imagen no es extremadamente grande, la cantidad de trabajo asignada a cada hilo puede ser insuficiente para amortiguar el overhead de gestión de hilos ya que las operaciones de sincronización pueden suponer un tiempo considerable en comparación con las operaciones de suma/multiplicación realizadas.
\end{itemize}
\vspace{3ex}

\subsection{Análisis de la versión SIMD}
Los resultados de la versión SIMD son especialmente sorprendentes: en lugar de mejorar el rendimiento,
 esta implementación resulta \textbf{0.74x más lenta} que la versión 
 monohilo original. Se ha comprobado en varios ordenadores con diferentes
  procesadores y, en todos, los resultados son similares. 
  Se ha verificado que todos ellos tuvieran soporte para las 
  instrucciones necesarias y que el código estuviera optimizado. Algunas posibles causas de este comportamiento incluyen:
\begin{itemize}
    \item \textbf{Overhead en la gestión de memoria}: La utilización de memoria alineada y las operaciones de carga/almacenamiento SIMD pueden introducir un overhead que no compensa la paralelización a nivel de datos, especialmente si el tamaño de los datos no es lo suficientemente grande.
    \item \textbf{Limitaciones del compilador}: Es posible que el compilador no esté optimizando adecuadamente el código SIMD, o que las instrucciones generadas no sean las más eficientes para el hardware específico.
\end{itemize}

Además, hemos probado a realizar el alogritmo utilizando la operación 
\texttt{\_mm\_fmadd\_pd()} en lugar de \texttt{\_mm\_add\_pd()}, pero la imagen generada 
era distinta respecto a la monohilo y multihilo. Esto creemos que se debe a 
que la instrucción \texttt{\_mm\_fmadd\_pd()} realiza la suma y la multiplicación en 
una operación combinada, es por ello que solo redondea una vez. A diferencia de hacer una instrucción
de suma y otra de multiplicación, que redondea dos veces, lo que provoca pequeñas diferencias en el resultado final.

\section{Flujo de trabajo y metodología de desarrollo}
Todo el desarrollo del proyecto se encuentra disponible en el repositorio de \textit{GitHub}: \href{https://www.github.com/Mendana/teamwork-ac-2025}{ver repositorio}. Para garantizar un trabajo colaborativo eficiente, se estableció un flujo de trabajo común basado en las herramientas \textit{Git} y \textit{GitHub} como elementos centrales de control de versiones. Los aspectos clave son:

\begin{itemize}
    \item \textbf{Repositorio compartido:} Contiene el código, la documentación y los recursos del proyecto.
    \item \textbf{Issues:} Cada tarea se define como una \textit{issue} en \textit{GitHub}, asignada a un responsable con una fecha límite.
    \item \textbf{Project Board:} Se emplea un tablero \textit{Kanban} con las columnas \textit{To Do}, \textit{In Progress}, \textit{Review} y \textit{Done} para visualizar el progreso del trabajo.
    \item \textbf{Milestones:} Cada entrega del proyecto se asocia a un \textit{milestone} que agrupa las \textit{issues} relacionadas.
    \item \textbf{Pull Requests:} Todas las contribuciones se integran mediante \textit{pull requests}, revisadas y aprobadas por, al menos, tres de los cuatro miembros del equipo antes de fusionarse en la rama principal.
    \item \textbf{Documentación:} Se conserva en la carpeta \texttt{docs/}.
\end{itemize}

\subsection{Metodología}
\label{anexo:metodologia}
El equipo adoptó una metodología ágil adaptada al contexto académico, inspirada en un enfoque híbrido entre \textit{Scrum} y \textit{Kanban}. Los elementos principales de esta metodología son:
\begin{itemize}
    \item La planificación se organiza en \textbf{iteraciones} (\textit{milestones}) que corresponden a las entregas del proyecto.
    \item Las tareas se dividen en \textbf{issues} manejables, priorizadas según su relevancia y dependencias, y se asignan a los miembros del equipo.
    \item El \textbf{Project Board} facilita la visualización del progreso y la gestión eficiente de las tareas.
    \item La revisión colectiva de los \textit{pull requests} promueve la calidad del código y el aprendizaje conjunto.
    \item Las dependencias entre tareas se gestionan mediante etiquetas y referencias cruzadas en \textit{GitHub}.
\end{itemize}
